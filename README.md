# TaskLine — мини-приложение сотрудников поддержки для MAX

Интерфейс сотрудников службы поддержки, который открывается внутри мессенджера MAX из чата
бота. Здесь сотрудники разбирают обращения клиентов с подсказками ИИ и отвечают им — ответ
приходит клиенту в чат бота.

Решение состоит из двух репозиториев:

| Репозиторий                                                                 | Что внутри                                                                                                 |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| [TaskLine-server](https://github.com/bounchich1/TaskLine-server)            | API, бот MAX, фоновые обработчики, ИИ-шлюз, OpenAPI, DATA-API, тестовые данные; **главный README решения** |
| [TaskLine-mini-app](https://github.com/bounchich1/TaskLine-mini-app) (этот) | мини-приложение (React 19, MAX UI)                                                                         |

Подробное описание всего решения — архитектура, внешние сервисы, работа с данными, тестовые
данные, API — в [README сервера](https://github.com/bounchich1/TaskLine-server#readme). Здесь —
то, что касается мини-приложения, и запуск всего решения из этого репозитория.

## Назначение

- очередь обращений с сортировкой по срочности, фильтрами, поиском по номеру и тексту;
- карточка обращения: переписка с фото, видео и файлами, подсказка ИИ (кратко, шаги,
  предостережения, ссылки на похожие решённые обращения), черновик ответа клиенту;
- команды: взять в работу, изменить тему/срочность/сложность, ответить с вложениями,
  передать коллеге, закрыть, переоткрыть, решить судьбу недоставленного ответа;
- уведомления и живое обновление (SSE) без перезагрузки;
- «Управление» для администратора: сотрудники и приглашения, справочники, шаблоны сообщений
  бота, настройки организации, журнал аудита; «Состояние системы» для руководителя;
- светлая и тёмная темы в стиле MAX, адаптивность от телефона до десктопа;
- публичная страница политики обработки данных `/legal`.

Интерфейс учитывает роль: кнопки и разделы, на которые нет прав, не показываются, а сервер
всё равно проверяет права на каждом запросе.

## Где попробовать в MAX

- **чат-бот** — бот хакатона, выданный организаторами (ссылка — в карточке решения);
- **мини-приложение** — кнопка в чате бота, адрес `https://demo.juicymelons.top/`;
- **роль сотрудника** — команда `/code <КОД>` в чате бота (коды ролей переданы организаторам),
  затем открыть приложение кнопкой в чате.

## Основной пользовательский сценарий

1. Клиент пишет боту, соглашается с политикой — появляется обращение с номером; ИИ
   проставляет тему, срочность, сложность и готовит подсказку.
2. Сотрудник открывает мини-приложение из чата бота: вход по подписанным данным запуска MAX,
   без паролей.
3. В очереди новое обращение сверху; сотрудник открывает карточку, читает переписку и
   подсказку ИИ, нажимает «Взять в работу».
4. Отвечает клиенту (можно подставить черновик ИИ и приложить файлы) — клиент получает ответ
   в чате.
5. Закрывает обращение — клиенту уходит запрос оценки; при необходимости передаёт обращение
   коллеге или переоткрывает.
6. Руководитель видит и чужие обращения и «Состояние системы»; администратор управляет
   сотрудниками, справочниками, шаблонами и настройками.

## Состав и архитектура

```
MAX (WebView) ──► мини-приложение (статика, Caddy :8080)
                     │  window.WebApp.initData ──► POST /v1/auth/max ──► token + csrf
                     ├─► REST /v1/*  (Bearer, X-CSRF-Token, Idempotency-Key, If-Match)
                     └─► SSE  /v1/events  ──► точечная перезагрузка данных
```

- Одностраничное приложение на React 19 и `@maxhub/max-ui`, данные — TanStack Query,
  таблица очереди — TanStack Table, стили — SCSS (BEM и токены темы).
- Приложение обращается только к API сервера (`/v1`) на том же адресе; ключей провайдеров и
  других секретов в нём нет.
- Образ: сборка Vite в Node 22, раздача Caddy на порту 8080; `index.html` не кэшируется,
  файлы с хэшем кэшируются на год (`deploy/Caddyfile`).
- Структура кода и правила зависимостей — [ARCHITECTURE.md](ARCHITECTURE.md).

## Запуск в Docker

Нужны Docker Engine 24+ (или Docker Desktop) с Docker Compose v2.24+ и доступ в интернет.

**Одна команда** (из корня этого репозитория) поднимает всё решение: мини-приложение
собирается из этой копии, сервер — из зафиксированного коммита TaskLine-server:

```bash
docker compose up -d --build
```

Через 1–2 минуты откройте `http://localhost:8080`. Поднимутся `postgres`, `redis`, `migrate`,
`seed` (тестовые данные), `api`, `worker`, `gateway`, `mini-app`, `web` (Caddy, единый адрес).
MAX и ИИ заменены заглушками. Собрать сервер из локальной копии:
`SERVER_SOURCE=../TaskLine-server docker compose up -d --build`.

Только образ мини-приложения:

```bash
docker build -t max-support-mini-app .
docker run --rm -p 8081:8080 max-support-mini-app
```

## Параметры окружения

- ОС: Linux, macOS или Windows 10/11 (Docker Desktop с WSL 2).
- Ресурсы: 2 ядра, 2 ГБ свободной памяти, 2 ГБ диска.
- Свободный порт `8080` (меняется переменной `WEB_PORT`).
- Приложение открывайте по `http://localhost:8080`: сервер принимает изменяющие запросы
  только с этого адреса.
- Для разработки: Node.js 22.22+, npm.

## Переменные окружения

Мини-приложение читает переменные только при сборке (Vite); секретов в `VITE_*` быть не должно.

| Переменная                      | По умолчанию         | Назначение                                                                     |
| ------------------------------- | -------------------- | ------------------------------------------------------------------------------ |
| `VITE_API_BASE`                 | пусто (тот же адрес) | адрес API, если он отличается от адреса приложения                             |
| `VITE_DEV_AUTH`                 | `false`              | вход без MAX через `/v1/auth/dev` — только в `npm run demo` (режим разработки) |
| `VITE_DEV_USER_ID`              | `1`                  | MAX ID для входа без MAX в режиме разработки                                   |
| `APP_VERSION` (аргумент сборки) | `dev`                | версия, видна в «Управление → Состояние системы»                               |

Переменные локального стека (`WEB_PORT`, `SERVER_SOURCE`, `MAX_MODE`, `AI_MODE`,
`DEMO_ROLE_CODES` и другие) задаются в `.env` рядом с `compose.yaml` и описаны в
[README сервера](https://github.com/bounchich1/TaskLine-server#переменные-окружения).
Шаблон переменных сборки — [.env.example](.env.example).

## Внешние сервисы и интеграции

- **MAX Bridge** (`window.WebApp`) — данные запуска для входа, кнопка «Назад», подтверждение
  закрытия при неотправленном черновике, размер окна, скачивание файлов. Работает только внутри MAX; вне MAX приложение
  показывает «Откройте мини-приложение через бота в MAX».
- **API TaskLine-server** — единственный источник данных. Внешние сервисы решения (MAX Bot API,
  LLM-провайдер) использует сервер — см. его README.

## Работа с данными

- Токен сессии и CSRF-токен хранятся только в памяти вкладки; после закрытия приложения
  нужен новый вход из MAX.
- Неотправленные черновики ответов живут до закрытия окна; при истечении сессии черновик
  сохраняется.
- В `localStorage` хранится только выбранная тема (светлая/тёмная/как в системе).
- Вложения скачиваются с авторизацией или по одноразовой ссылке сервера.
- Тестовые данные (6 обращений) загружает сервер — сервис `seed` локального стека, файл
  `test-data/max-updates.json` в TaskLine-server.

## Пошаговый сценарий проверки

**В MAX (демо-стенд):**

1. Напишите боту вопрос и согласитесь с политикой — бот сообщит номер обращения.
2. Отправьте боту `/code <КОД_SUPPORT>` и откройте приложение кнопкой в чате.
3. Убедитесь, что обращение в очереди с темой и срочностью; откройте его — видна переписка
   и подсказка ИИ.
4. «Взять в работу» → напишите и отправьте ответ: он придёт вам в чат бота.
5. Закройте обращение — бот попросит оценку.
6. `/code <КОД_ADMIN>`, откройте приложение заново — появятся «Управление» и «Состояние
   системы».

**Локально:**

```bash
docker compose up -d --build
curl -s http://localhost:8080/health/ready
```

Ожидается `{"status":"ready","version":"local"}`. `http://localhost:8080` в браузере покажет
экран «Вход не выполнен. Откройте мини-приложение через бота в MAX…» — вне MAX так и должно быть;
`http://localhost:8080/legal/` — страница политики. Проверка API с тестовыми данными — в
[README сервера](https://github.com/bounchich1/TaskLine-server#локально-в-docker).

**Интерфейс без MAX (разработка)** — с сервером, запущенным локально по его README
(`npm run dev:all`, `DEV_AUTH_ENABLED=true`):

```bash
npm ci
npm run demo
```

Приложение на `http://127.0.0.1:5173` войдёт как сотрудник с MAX ID `1`.

## Известные ограничения

- Вход только из MAX (подписанные данные запуска); в браузере без MAX — только режим
  разработки `npm run demo`.
- Сессия — до 8 часов, завершается после 30 минут бездействия; приложение предложит открыть
  его заново.
- Нужен сервер TaskLine-server: без API приложение не работает.
- Интерфейс только на русском.

## Остановка и повторный запуск

```bash
docker compose stop            # остановить, данные сохраняются
docker compose start           # запустить снова
docker compose down            # удалить контейнеры, тома остаются
docker compose up -d --build   # пересобрать и поднять
docker compose down -v         # удалить всё вместе с данными
```

## Разработка

```bash
npm ci
npm run dev               # против сервера на 127.0.0.1:3000 (прокси /v1)
npm run demo              # вход через /v1/auth/dev (сервер с DEV_AUTH_ENABLED=true)
npx playwright install chromium   # один раз, для тестов
npm run check             # форматирование, ESLint, Stylelint, типы, knip, тесты, сборка
```

## Развёртывание

`Dockerfile` собирает приложение и раздаёт его Caddy на порту 8080. Тег `v*` собирает образ
`ghcr.io/<owner>/max-support-mini-app:<tag>` с этой версией и при настройке разворачивает его.
Продакшн-стек и инструкции — в репозитории сервера: `deploy/` и `runbooks/deploy.md`.
